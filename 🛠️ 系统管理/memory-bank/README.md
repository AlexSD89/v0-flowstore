# LaunchX Memory Bank 导航

> 使命：把零散资产沉淀成可复用的系统记忆，支撑 Codex ↔ Claude 的协同闭环。

---

## 1. Memory Bank 在协作中的角色
- **系统级复用仓**：存放跨项目、跨目录可复用的知识、脚本与方法论。
- **互链枢纽**：所有引用需在 Summary 中标注来源，并在相关 README/USEME 内建立双向链接。
- **版本记录器**：重要更新需记录来源、责任人、时间，便于溯源与回滚。

---

## 2. 目录结构与颗粒度
| 子目录 | 说明 | 典型内容 |
| --- | --- | --- |
| `support_modules/` | 跨项目通用模块、提示片段、脚本 | `USEME.md`、最小示例、依赖说明 |
| `scripts/` | 自动化脚本与质量检查工具 | 路径对齐检查、数据验证、质量门控 |
| `MCP服务资产库/` | 已配置或在筹的 MCP 服务档案 | 接入指南、Token 策略、风险提示 |
| `indexes/`（预留） | 领域/项目索引与导航 | TODO｜待补充 |
| 其他补充目录 | 根据需求新增，须在此 README 备案 | 定制方法论、评测脚本等 |

> **颗粒度要求**：同类素材放在同一层级，文件命名遵循 `YYYYMMDD-主题.md`，避免重复造轮子。

---

## 3. 路径对齐强制管理
- **零容忍原则**：任何support_modules中的路径引用不一致问题都必须立即修复
- **强制验证机制**：
  - 每次Phase 0认知加载必须执行路径对齐验证
  - 检查所有USEME.md中的路径引用与实际目录结构一致性
  - 验证所有@AT引用路径存在性和可访问性
- **问题处理流程**：
  - 发现路径不一致时立即报错并中止执行
  - 记录路径对齐检查结果和修复计划
  - 修复完成后重新验证并记录在案
- **质量门控**：路径对齐不通过不得进入任何执行阶段
- **检查工具**：使用 `scripts/path-alignment-check.sh` 自动化验证路径一致性

## 4. Codex 与 Claude 的使用指引
- **Codex 侧**：
  - Phase 0 必须检查目标资源是否已存在，缺口以 "TODO｜待补充 + 缺口来源" 标注再行动。
  - 仅在需要新增资产时创建最小版本，并在 Summary 中抄送 Memory Curator。
  - **路径对齐检查**：每次操作前必须验证support_modules中的路径引用正确性
- **Claude 侧**：
  - Skills/Hooks 调用必须引用对应的 memory-bank 条目，如材料缺失需先补档再执行。
  - 自动化输出的脚本或模板，需在 24h 内回写至 memory-bank 并关联 README。
  - **路径一致性维护**：确保所有引用路径与实际文件结构完全一致
- **交接原则**：任一方引用/更新 memory-bank，另一方需在下一轮 Summary 中确认已读取。

---

## 5. 更新与互链规范
- **新增文件**：写明创建原因、复用场景与验证方式；补充 `related` 字段保持可追溯。
- **引用登记**：在被引用目录（如 `📖README-LaunchX系统总体指南.md`、目标域 README）标注来源。
- **巡检节奏**：每月至少一次针对活跃项目的条目抽查，确认是否需要归档或升级。
- **归档标准**：超过 90 天未使用、且无当前项目依赖的资料，迁移至 `archives/` 并在此 README 记录。

---

记忆仓不是堆砌资料的盒子，而是让协作更聪明的“第二大脑”。保持条目精炼、引用清晰，就是对全体协作者最大的助力。

# Gate OS 内核 · 总体架构设计

> 视角：本文件站在 Gate OS 的角度，看待 CA Code / Claude Code 作为底层操作系统，
> 小红书等项目作为 SDK；Gate OS 自身是中间层“内核”，负责调度、证据、自治等级和流程编排。

## 1. Gate OS 在三层结构中的位置

### 1.1 三层回顾

- **底层：CC / Claude Code**
  - 负责：
    - 5 步认知法引擎（Collect / Model / Compare / Align / Deliver）；
    - Skills/Hooks/MCP 的原生执行环境；
    - Dev Docs / 文件系统 / 网络 / 缓存等基础能力。

- **中间层：Gate OS 内核（本文件）**
  - 负责：
    - Agent 生命周期管理与调度；
    - Skills 注册与组合编排；
    - 证据账本与自主等级（LOA）管理；
    - 工作流编排（Workflow Orchestration）。

- **上层：Project / Client SDK**
  - 负责：
    - 领域项目（如小红书运营）的业务模型；
    - 具体的 Spec 模板 / 流程模板 / 内容模板；
    - 面向 Gate OS 的“意向包（Intent Package）”与配置。

Gate OS 内核不写具体业务规则，只提供“如何运行”和“如何决策”的能力；
Project/Client SDK 才携带“为谁服务”和“业务是什么”。

## 2. Gate OS 内核的四大职责

Gate OS 内核被拆成四个核心职责域，每个职责域对应一组模块：

1. **AgentRuntime（Agent 运行时）**
   - 启动 / 停止 / 监控 Agent；
   - 管理并发与资源；
   - 提供 Agent 间通信总线。

2. **SkillsEngine（技能注册与执行引擎）**
   - 负责 Skills 注册 / 发现 / 调用；
   - 支持跨项目的通用技能与项目特定技能；
   - 和 CC 层的 Skills 生态做映射（不重复造轮子）。

3. **Evidence & LOA（证据账本与自主等级）**
   - 记录关键信息的证据链（来源、类型、置信度）；
   - 管理不同任务的 LOA 等级（LOA0–LOA4）；
   - 在执行前根据证据与风险决定“自动 vs 人类确认”。

4. **WorkflowOrchestrator（工作流编排）**
   - 接收来自 SDK 的意向包（Intent Package）；
   - 选择合适的 Agent / Skills / 工具链；
   - 执行 5 步认知流程并回写结果到 Spec / 文档 / 数据。

后续在 `01-模块与接口设计.md` 中会把这四块拆成更具体的类与接口设计（仅设计，不要求立刻实现）。

## 3. Gate OS 内核与 Project / Client SDK 的关系

### 3.1 意向包（Intent Package）

- Project/Client SDK 负责生成“意向包”：
  - 内含：
    - 任务类型（例如：`generate_xhs_post` / `run_weekly_plan` / `run_trending_learning`）；
    - 关联的 Spec 路径（Post Spec / Weekly Plan / Client SDK）；
    - 约束与偏好（如 LOA 级别、允许调用的工具集合）。

- Gate OS WorkflowOrchestrator 只认“意向包”，不直接读乱七八糟的文件；
  - 它会：
    - 根据任务类型选路由；
    - 将路径交给 CC 层的 Dev Docs/文件系统工具来解析；
    - 通过 SkillsEngine 调用具体的 Skills/MCP。

### 3.2 典型调用链（以小红书 Post 为例）

1. Client SDK（LaunchX_XHS）
   - 读 `client-sdk-launchx.md` 确认品牌约束 / KPI。
   - 读某个 `post-*.md`（Post Spec）生成意向包：
     - 任务：`generate_and_publish_post`
     - 输入：Spec 路径、Client Slug、内容任务类型 C1–C4、Pattern ID。

2. Gate OS
   - WorkflowOrchestrator 接收意向包；
   - Evidence & LOA 模块根据风险/证据决定是否自动发布；
   - AgentRuntime 调度对应的“内容生成 Agent”和“发布 Agent”；
   - SkillsEngine 通过 `xiaohongshu-mcp` 完成发布。

3. 结果回写
   - Gate OS 将 note_id / note_url 等输出回写到 Spec；
   - 同时写入数据管道与 Experiment Log，供演化系统使用。

## 4. 与现有代码的对齐（只做映射，不强制重构）

> 目的：让之后写的代码都能找到归属，而不是“到处写脚本”。

目前仓库中已有一些 Gate OS 内核相关的雏形代码，例如：

- `src/core/workflow_engine.py`
- `src/tools/four_dimensional_data_collector.py`
- `src/tools/evidence_ledger.py`
- `src/agents/autonomy_level_management.py`

我们不要求一次性重构到“完美的 Gate OS 模块树”，
但要求：

1. 新增能力时，先在 `gate-os/01-模块与接口设计.md` 中确定归属（AgentRuntime / SkillsEngine / Evidence&LOA / WorkflowOrchestrator）。
2. 对现有文件做演进时，在本文件或 01 文档中补充映射说明（例如：某个类现在算作 WorkflowOrchestrator 的一部分）。

## 5. 命名与文件路径约定（设计层）

为了 Gate OS 层在不同项目间可复用，命名与路径保持领域无关、项目无关：

- 目录建议（代码侧，仅作为未来实现参考）：
  - `src/gate_os/agent_runtime.py`
  - `src/gate_os/skills_engine.py`
  - `src/gate_os/evidence_ledger.py`
  - `src/gate_os/autonomy_manager.py`
  - `src/gate_os/workflow_orchestrator.py`

- 文档路径（本目录）：
  - `gate-os/00-总体架构.md`（本文件）
  - `gate-os/01-模块与接口设计.md`

未来在实现层真正落代码时，只需要对照这些文档检查：

- 是否命名和职责与这里描述的一致；
- 是否保持 Gate OS 与 Project/Client SDK 的清晰边界。

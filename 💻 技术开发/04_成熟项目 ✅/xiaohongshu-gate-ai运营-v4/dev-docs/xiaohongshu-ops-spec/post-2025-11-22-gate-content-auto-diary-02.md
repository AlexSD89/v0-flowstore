## 4. 正文结构

- 第一屏（前 2–3 行，钩子）：
  - 针对的用户画像：
    - 想认真做内容但精力有限的小团队负责人 / 创始人；
    - 想把内容当资产而不是负担的产品/运营/工程师；
  - 提出什么冲突/问题：
    - 「每个团队都有写不完的内容，但没人有精力把同一篇内容改成 4 个平台的版本。」

  草稿示意：
  > 「说实话，我们自己也很难坚持写内容。\n  >  真正痛的不是写一篇，而是——一篇内容要改成小红书、公众号、即刻、内部社群四种版本，最后谁来发？」

- 主体结构（建议 3–5 段，每段 2–4 行）：

  1. 场景描述：
     - 讲 LaunchX 自己的状况：有很多方法论、项目复盘，但落地到内容非常吃力；
     - 每一次发小红书/公众号，都要花一堆脑力在「改格式」「改语气」「改结构」。

  2. 冲突/痛点：
     - 内容创作不是没有东西写，而是被「渠道碎片化」和「重复劳动」耗光精力；
     - 作为做 Gate 的团队，如果自己都不能把内容自动化做出来，会觉得很违和。

  3. 解决思路或拆解：
     - 先从 n8n 那边学习：
       - 看他们如何设计「社交媒体管理 / 内容自动发」工作流；
       - 提炼出：输入源 → 内容处理 → 多平台发布 → 日志/数据回收 这 4 个关键步骤；
     - 再在 Gate 里设计一个属于自己的三层架构版本：
       - 上层：内容源 & 模板库；
       - 中层：Gate 自动化工作流 + AI 改写 / 风格适配；
       - 下层：多平台发布 + 数据回收。

  4. 具体步骤/细节：
     - 说明我们现在的一条 Gate 内容自动化链路：
       1. 在一个地方（MD/Obsidian/Notion）写「长版内容」；
       2. Gate 调用 AI，自动生成小红书版/公众号版/即刻版的不同结构和语气；
       3. Gate 调度 MCP/API，把内容定时发到各个平台；
       4. 把平台的表现数据（阅读、收藏、评论）回收到 Gate，用来决定下周写什么/怎么改。

  5. 结果/反馈（如有）：
     - 讲过去 2–4 周的实际体验：
       - 发文频率更稳定了（不用纠结“今天谁有空发”）；
       - 团队反而有空去深挖一个问题，而不是被“发内容”本身拖住；
       - 小红书/其他平台的某些结构/写法被证明更好用（为下一期日记埋伏笔）。

- 结尾（CTA）：
  - 想让读者做什么：
    - [x] 评论  [x] 收藏  [ ] 点赞（自然会有）  [x] 私信  [ ] 关注
  - CTA 文案候选：
    - 「你现在每周发几条内容？你最痛的是“写”还是“发”？评论里可以聊聊，我们后面会拆 Gate 的整个内容工作流。」
    - 「如果你正准备给自己做一个 n8n / Make 内容工作流，也可以私信【内容自动化】，我们可以把我们踩过的坑整理一篇给你。」

- Markdown / 文本约束：
  - 最长不超过 800 字，尽量按「短段 → 空行」方式排版；
  - 重要句子单独成段，避免在同一段堆太多信息；
  - 避免堆砌技术细节（节点名、API 名等），重点在场景与感受。

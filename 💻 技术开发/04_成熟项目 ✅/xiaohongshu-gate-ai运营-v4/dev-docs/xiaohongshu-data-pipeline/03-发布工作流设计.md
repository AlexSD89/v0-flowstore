# 小红书内容发布工作流设计（基于 Post Spec + xiaohongshu-mcp）

> 本文件回答：当我们已经有一篇结构化的 Post Spec（如 Gate 场景日记 02），如何在不打开浏览器的前提下，
> 由 Claude / Gate OS 调用 `xiaohongshu-mcp` 完成真实发布，并把结果写回到文档与数据系统中。

## 1. 输入与输出总览

### 1.1 工作流输入：Post Spec

- 主要输入文件：
  - `dev-docs/xiaohongshu-ops-spec/post-*.md`，例如：
    - `post-2025-11-22-gate-finance-diary-02.md`
- 必须包含的关键信息（在 `post-template.md` 中已有字段，执行前需补全）：
  - 基本信息：
    - `client_slug`（如 `launch-x`）
    - 内容任务类型（C1/C2/C3/C4）
  - 标题与结构：
    - 最终发布标题（需满足小红书长度限制）
    - 正文段落（已按 Pattern 组织好）
  - 标签与话题：
    - 按 `TagEngine-LX-2025Q4` 等规则生成的标签字段
  - 媒体资源：
    - 图片数量、文件名/路径占位（如 `assets/xhs/gate-finance-02/*.png`）
  - 发布策略：
    - 是否立即发布 / 定时发布
    - 是否开启评论 / @ 特定账号（如有）

> 说明：Post Spec 是「人类可读 + 机器可解析」的单一事实源，Gate-AI-XHS 发布官只关注这篇文档里的标题和正文是否满意，
> 其余字段由 Claude / Codex 通过模板和工具自动补齐。

### 1.2 工作流输出：平台状态与本地记录

- 小红书平台侧（由 `xiaohongshu-mcp` 返回）：
  - 笔记 ID（note_id）
  - 笔记链接（note_url）
  - 发布时间（publish_at）
  - 平台返回的基础统计字段（如有：初始曝光值、状态等）

- 仓库/数据系统侧：
  - Post Spec 更新：
    - 在对应 `post-*.md` 文件中追加「实际发布信息」小节，保存 note_id / note_url / 发布时间；
  - 数据留存：
    - 在 Client 目录下写入一条发布记录：
      - `clients/<slug>/data/performance/publish_log_YYYYMMDD.json`
    - 内容包括：Post Spec 路径、note_id、note_url、发布时间、执行 Agent 等。

## 2. 从 Post Spec 到 MCP 调用的映射

### 2.1 字段映射概览

下表定义 Post Spec 与 `xiaohongshu-mcp` API/CLI 参数的核心映射关系（具体字段名以 tools README 为准）：

| 维度 | Post Spec 字段（示例） | MCP 请求字段（示例） | 备注 |
|------|------------------------|-----------------------|------|
| 标题 | `title_final`          | `title`               | 需满足 20 字以内限制 |
| 正文 | `body_final`           | `desc` / `content`    | 建议控制在 1000 字以内 |
| 标签 | `tags`（数组）         | `tags` / `topic_list` | 由 Tag Engine 输出 |
| 媒体 | `images[]`             | `image_paths` / `files` | 本地路径或已上传资源标识 |
| 客户 | `client_slug`          | `extra.client_slug`   | 便于日志/数据关联 |
| 场景 | `content_types` / `patterns` | `extra.scene`   | 用于后续分析与实验关联 |

> 注意：具体参数名和限制以 `🧰 tools/xiaohongshu-mcp/README.md` 为准，本文件只定义概念映射和约束。

### 2.2 标题与正文的约束

- 标题（`title_final`）：
  - 来源：Post Spec 中经 Gate-AI-XHS 发布官最终确认的标题字段；
  - 约束：
    - 长度建议 ≤ 20 个中文字符（参考 MCP README 中小红书平台要求）；
    - 尽量在标题中体现核心场景与人设，而非仅出现品牌名。

- 正文（`body_final`）：
  - 来源：Post Spec 中的正文草稿，经人类少量调整后定稿；
  - 约束：
    - 总长度建议 ≤ 1000 字；
    - 分段清晰，可直接复制到小红书编辑器不需要再手调结构。

### 2.3 标签与话题

- 生成方式：
  - 优先使用 Client SDK 中定义的 Tag Engine（如 `TagEngine-LX-2025Q4`）；
  - 根据 Post Spec 中的 `tag_mode`（保守/平衡/进攻）、内容类型（C1–C4）与场景，自动组合标签；
  - 保证每篇内容同时包含：品牌标签 + 功能标签 + 热门流量标签 + 部分长尾标签。

- 写回方式：
  - 在 Post Spec 中保留最终使用的标签列表；
  - 在发布日志中记录标签数组，作为后续 Experiment Log 的输入。

## 3. 发布工作流分步设计

本节以「Gate 场景日记 02｜财务月底结账」为例，描述从 Spec 到平台的典型流程。实际执行由 Claude / BMAD 完成，Codex 仅负责文档与约定。

### 3.1 准备阶段（人类 + Codex）

1. **选定场景与范式**：
   - 根据 `Search Spec`（如 `client-sdk-launchx.md` 中的 Search 部分），
     先在小红书等平台搜索相近场景的高表现内容（如 n8n 财务自动化案例）。
   - 在 Pattern Library 中选择适配的标题/正文/内容类型范式（如 P-Title-01, P-Body-01, P-Content-01）。

2. **撰写 Post Spec 初稿**：
   - 使用 `post-template.md`，填入：场景描述、结构化正文、预期标签模式等；
   - Gate-AI-XHS 发布官只关注「标题 + 正文」是否足够具体、有人味。

3. **Spec 定稿**：
   - 发布官确认：
     - 标题满足平台限制且足够「性感」；
     - 正文表达清晰、场景具体、有画面感；
   - 其余字段（标签、images 占位、发布策略）由 Codex/Claude 根据模板补全。

### 3.2 执行阶段（Claude / Gate OS + xiaohongshu-mcp）

> 以下步骤在实际运行时由 Claude / BMAD 执行，本文件只描述意图与数据流，具体命令在 Claude 侧 Hooks 中实现。

1. **解析 Post Spec**：
   - 从 `post-*.md` 中抽取：标题、正文、标签、图片路径、client_slug 等字段；
   - 根据 `02-数据留存与访问规范.md` 中的路径约定，准备好需要上传的媒体文件。 

2. **构造 MCP 请求**：
   - 将抽取结果映射到 `xiaohongshu-mcp` 的发布接口参数；
   - 检查：
     - 标题/正文长度是否在允许范围内；
     - 标签数量是否过多/过少；
     - 媒体文件是否可访问。

3. **调用 `xiaohongshu-mcp` 发布**：
   - 使用 tools README 中推荐的方式（CLI 或 HTTP）发起发布；
   - 捕获返回的 note_id / note_url / 状态码与错误信息；
   - 若失败，记录日志路径并交由人类介入排查（见 `launch-x_run_checklist.md`）。

4. **写回结果**：
   - 更新 Post Spec：
     - 追加一个「实际发布信息」小节，包含：note_id、note_url、publish_at、执行 Agent、版本号等；
   - 更新 Client 数据：
     - 在 `clients/<slug>/data/performance/publish_log_YYYYMMDD.json` 中追加记录；
   - 可选：
     - 在 `experiment-log-LaunchX-2025Q4.md` 中创建对应实验条目，记录本次发布的假设与后续观测计划。

### 3.3 观察与演化阶段（数据系统 + Evolution 层）

1. **收集表现数据**：
   - 通过 `XHS_AccountPerformanceCollector` Agent 定期抓取该 note 的曝光/点赞/收藏/评论等指标；
   - 将结果写入 `clients/<slug>/data/performance/account_metrics_YYYYMMDD.json`。

2. **回写 Experiment Log**：
   - 在 `experiment-log-LaunchX-2025Q4.md` 中，为该 Post 新增一条实验记录：
     - 关联的 Post Spec 路径；
     - 使用的内容类型（C1/C2/C3/C4）与 Pattern；
     - 初始表现数据（7 天 / 30 天）与结论；
     - 对 Pattern Library / Tag Engine 的影响（保留/调整/废弃）。

3. **影响下一轮内容与 Search Spec**：
   - 若本条 Gate 场景日记表现良好：
     - 将其写入 Pattern Library 中作为「高优先级范式」；
     - 在 `client-sdk-launchx.md` 的 Search Spec 中记录：本场景可作为后续相似行业/流程的优先参考案例。

## 4. Codex vs Claude 职责边界

### 4.1 Codex（本地 CLI）

- 负责：
  - 维护本文件及相关 Dev Docs 的结构与约定；
  - 在新增/修改 Agent 或工具时，更新字段映射与路径约定；
  - 确保 Post Spec 模板与发布结果字段一致。
- 不负责：
  - 实际调用 `xiaohongshu-mcp` 或处理登录态；
  - 运行 BMAD/Hook，或直接与外网 API 交互。

### 4.2 Claude / Gate OS

- 负责：
  - 基于本文件与 `01-Agent与工具架构设计.md`，实现具体的调度脚本与 Hooks；
  - 处理所有与 MCP/网络相关的执行细节与异常重试；
  - 将执行结果按约定写回 Post Spec、publish_log、Experiment Log 等位置。

> 总结：Codex 管「规则与结构」，Claude 管「执行与搜索」，Gate-AI-XHS 发布官只看「内容最后长什么样」。
